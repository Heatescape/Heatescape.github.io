Section 01

The guardrails are the portfolio

Four controls I designed and built. Each one exists because of a specific way the system could have hurt the business.

CTRL-01 Traceable

Audit logging on every write to live data

Every write to live data is recorded to an audit log and remains traceable after the fact. If something appears on the public portal, there is a record of what put it there and when.

Design note Traceability is worth nothing if it only covers the happy path. The log sits on the write itself, not on the intent to write.

CTRL-02 Auto Review queue

Risk based approval routing

Actions are routed by risk. Low risk publishes automatically. High risk goes to a human review queue, surfaced in the dashboard for a person to accept or reject.

Design note Human in the loop on everything means people rubber stamp. Routing by risk keeps human attention where it changes the outcome.

CTRL-03 Blocked a real incident

A concurrency guard that re validates the source before writing

The guard re validates the source immediately before the write, so an approval given against a stale preview is rejected rather than published.

That control caught and blocked a real stale write incident in production.

Incident, blocked A human approved a change against a preview that was no longer current. The pre write check rejected it. Nothing reached the public portal.

CTRL-04 Privilege separation

The language model is kept out of the permission layer

In the CRM assistant, the identity used for a query is set by the authenticated session and can never be supplied by the model, so it cannot query on behalf of another user.

Design note A model that can name its own caller is a model that can be talked into naming someone else. The identity never enters the prompt surface.
Confidentiality

Sensitive commission data filtering

Confidential commission figures are kept off the public portal, alongside versioned compliance archiving of every published price list.

Bounded agency

Agent loop capped, every tool call traced

The agent loop is bounded to a maximum of 6 tool calls. Every tool call is traced with its arguments and a result summary for after the fact review.

Anti hallucination

A faithfulness constraint in the data contract

The assistant must state when no option matches the buyer's budget before listing near misses, rather than relying on prompt instructions to keep it honest.

Regression testing

206 automated test files on the portal platform

Including regression suites built from real sample PDFs, so support for a new developer format cannot quietly break an old one.

Section 02

The write path

How a developer price list becomes a correct row on a public property portal, and where it gets stopped.

  1. Stage 1 / Collect Ingest from heterogeneous channels

    Developer price lists and floor plans arrive through Dropbox, Box, Gmail and custom web portals. Roughly 30 developer file formats.

  2. Stage 2 / Extract Hybrid rule based and LLM extraction

    80 to 90 column name variations handled, with a Gemini backed fallback for PDFs that rule based parsing cannot read. Property type is auto detected, apartment, townhouse, house and land, land only, and type specific field mapping is applied.

  3. Stage 3 / Match Fuzzy matching and record linkage

    Records are matched against existing stock. Ambiguous matches are the dangerous ones, so they are resolved explicitly rather than guessed.

  4. Stage 4 / Route by risk Risk based approval routing
    • Low risk Publishes automatically, and is still written to the audit log.
    • High risk Enters the human review queue in the dashboard and waits for a person.
  5. Stage 4b / Pre write check Concurrency guard re validates the source

    An approval given against a stale preview is rejected rather than published. This control caught and blocked a real stale write incident in production.

  6. Stage 5 / Publish and notify Write, log, archive, tell someone

    The write is recorded to the audit log and remains traceable after the fact. Commission figures are filtered out of anything public, and every published price list is archived with a version for compliance.

SPEC-01

Portal update automation platform

In production

Python / FastAPI / Azure SQL / Azure Blob Storage / Dropbox API / scheduled unattended operation / web dashboard

A five stage ETL pipeline, collect, extract, match, publish, notify, that ingests developer price lists and floor plans from heterogeneous channels and publishes to the company's live public property portal. The dashboard gives staff manual control, live monitoring and human review.

  • Multi source data reconciliation. I reconciled pricing and availability across four disconnected sources: the authoritative price list, marketing floorplates, archived files and the live public portal. It surfaced data quality problems nobody had reported, including seven units carrying the price of a different building, and sold stock still publicly listed. The drift came from system handoffs, not careless data entry, so the fix was a scheduled reconciliation rather than a one off cleanup.
  • Verified against reality, not a dry run. The first source taken fully to production was confirmed record by record against the live portal.

SPEC-02

Agentic AI voice assistant, in the company CRM

Feature complete, pending compliance sign off

ASP.NET Core 8 / .NET MAUI (Android) / Google Gemini 2.5 Flash / Azure SQL / JWT authentication

Sales agents speak or type a question in English, Chinese or a mix of both, and the assistant either answers it or files the follow up note against the client record. It covers property search, affordability and loan calculations, and client log updates in one chat surface on the mobile app, replacing thumb typing in the field and switching between five separate screens. It is feature complete, pending compliance sign off and production authentication cutover.

  • A tool calling agent, not similarity search. Structured retrieval through tool calls rather than similarity search. For a sales tool quoting prices and availability, similarity is the wrong primitive. The data has to be exact and live, so the model picks the tool and fills the parameters, and SQL does the rest.
  • Intent recognition and slot filling. The language model turns natural language into typed search criteria, then selects from roughly 12 deterministic tools that query Azure SQL. The model never generates a figure itself. Speech to text runs multimodal through Gemini with schema constrained output.
  • Bilingual understanding. English, Chinese, or a mix of both inside the same sentence.

Auto Tenant Check, and the AI market analysis assistant

In production, adopted daily

Playwright / Vision OCR / GraphQL API integration / Python / LLM report generation / installable Windows application
